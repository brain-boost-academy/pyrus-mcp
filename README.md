# pyrus-mcp

MCP-сервер поверх официальной библиотеки [`pyrus-api`](https://pypi.org/project/pyrus-api/).
Даёт LLM-агенту доступ ко всем 41 методу Pyrus API через stdio и защищает данные
трёхуровневым режимом доступа.

Ключевое свойство: **фильтрация происходит на этапе регистрации инструментов, а не в
рантайме**. Запрещённого в текущем режиме метода нет в `tools/list` — для модели он
не существует, и никакая галлюцинация до него не дотянется.

## Установка

```bash
uv sync
```

Требуется Python 3.14.

## Конфигурация

| Переменная | Обязательна | Назначение |
|---|---|---|
| `PYRUS_LOGIN` | да | логин (email) в Pyrus |
| `PYRUS_SECURITY_KEY` | да | секретный ключ |
| `PYRUS_PERSON_ID` | нет | если у логина несколько профилей |
| `PYRUS_ACCESS_TOKEN` | нет | переиспользовать готовый токен |
| `PYRUS_MCP_MODE` | нет | режим доступа, по умолчанию `non-destructive` |
| `PYRUS_MCP_FILE_ROOT` | нет | каталог-песочница; без него `upload_file` не регистрируется |
| `PYRUS_MCP_MAX_RESULT_BYTES` | нет | предел размера ответа, по умолчанию 262144 |

Режим определяется в порядке: `--mode` → `PYRUS_MCP_MODE` → `non-destructive`.
Неизвестное значение — выход с ненулевым кодом, без молчаливого отката.

Пример для MCP-клиента:

```json
{
  "mcpServers": {
    "pyrus": {
      "command": "uv",
      "args": ["run", "--directory", "/путь/к/pyrus-mcp", "pyrus-mcp", "--mode", "read-only"],
      "env": {
        "PYRUS_LOGIN": "you@example.com",
        "PYRUS_SECURITY_KEY": "..."
      }
    }
  }
}
```

## Режимы доступа

| Режим | Инструментов без `PYRUS_MCP_FILE_ROOT` | с заданным |
|---|---|---|
| `read-only` | 22 | 22 |
| `non-destructive` (по умолчанию) | 38 | 39 |
| `full` | 40 | 41 |

- **`read-only`** — только чтение. Сюда входит `download_file`: он возвращает содержимое
  вложения инлайн и ничего не пишет на диск.
- **`non-destructive`** — чтение и запись. Методы, уничтожающие данные, отсутствуют,
  а у четырёх пишущих методов проверяется payload (см. ниже).
- **`full`** — всё, включая `delete_role` и `delete_knowledge_base_entity`.

Режим фиксируется при старте процесса и записывается в `instructions` сервера, чтобы модель
знала, где находится. Сменить режим можно только перезапуском — это и есть гарантия.

## Граница `non-destructive`

Граница проходит **по потере данных, а не по названию метода**. Поэтому `sync_catalog`
доступен, а `delete_role` — нет, и поэтому проверка идёт до уровня полей payload.

### Что блокируется

| Метод | Отклоняется |
|---|---|
| `update_catalog_items` | непустой `delete` — удаление строк справочника |
| `sync_catalog` | всё, кроме явного `apply: false` |
| `update_role` | непустой `removed_members`; `banned` в любом значении, кроме `false` |
| `update_member` | `banned` в любом значении, кроме `false` |

Проверки построены как **allowlist**: проходит только явное `false` или отсутствие ключа.
`{"banned": "true"}` и `{"banned": 1}` отклоняются наравне с `true`.

Отдельно про `sync_catalog`: параметр `apply` по умолчанию `None`, и пропущенный ключ
сервер Pyrus трактует как «применить». Проверка «отклонять, если `apply == true`» была бы
безвредна ровно на том вызове, который стирает справочник, — поэтому проходит только
явное `apply: false`, то есть настоящий dry-run.

### Что разрешено осознанно

`non-destructive` **не** означает «ничего не меняется». Разрешены:

- изменение состава задачи — `comment_task` с `participants_removed`, `approvals_removed`,
  `removed_list_ids`. Это правка задачи, а не уничтожение записи;
- **перезаписи содержимого**:
  - `comment_task.edit_comment_id` — правка текста существующего комментария,
  - `comment_task.field_updates` — перезапись значений полей формы,
  - `update_knowledge_base_entity.body` — замена статьи целиком,
  - `update_catalog_items.upsert` — перезапись значений существующих строк справочника.

  Guard'ов на них нет намеренно: Pyrus хранит историю правок, поэтому прежнее значение
  восстановимо;
- изменение прав — `change_form_permissions`, `update_knowledge_base_permissions`.

> ⚠️ Изменение прав формально обратимо, но отзыв прав у последнего пользователя, который мог
> их выдавать, способен закрыть доступ к форме или разделу базы знаний так, что вернуть его
> изнутри уже нельзя. Если агент работает с правами — держите `read-only` или проверяйте
> вызовы вручную.

## Файлы

`upload_file` читает локальный файл, то есть является примитивом чтения с диска. Поэтому он
регистрируется **только** при заданном `PYRUS_MCP_FILE_ROOT`, а путь резолвится через
`Path.resolve()` и обязан лежать внутри корня: переходы через `..` и символические ссылки
наружу отклоняются.

`download_file` в песочнице не нуждается — он возвращает содержимое инлайн (текст как есть,
бинарные данные в base64) и на диск ничего не пишет. `set_avatar` принимает guid, полученный
от `upload_file`, а не путь.

## Большие ответы

Если ответ не влезает в `PYRUS_MCP_MAX_RESULT_BYTES`, сервер режет самый длинный список
верхнего уровня и добавляет блок `_pagination` с `total`, `returned` и `next_offset`. Данные
никогда не усекаются молча: модель всегда знает, что видит окно, и знает общий размер.
У читающих инструментов есть параметр `offset` — с ним запрашивается следующее окно.

## Формы вызова

Ключи payload не захардкожены: они снимаются с `pyrus-api` через `inspect.signature`
на импорте и попадают в описание инструмента. Неверный ключ возвращает ошибку со списком
валидных и пометкой, какие обязательны, — модель исправляется сама.

| Форма | Сигнатура инструмента |
|---|---|
| `PLAIN` | `(options?, offset?)` |
| `BY_ID` | `(entity_id, options?, offset?)` |
| `REQ` | `(request, offset?)` |
| `ID_REQ` | `(entity_id, request?, offset?)` |

Исключение — `create_member` и `update_member`: их request-классы в `pyrus-api` объявлены
как `**kwargs` над `entities.Person`, который молча выбрасывает незнакомые ключи. Список
ключей всё равно попадает в описание, но опечатка там не вызовет ошибки ни на стороне
сервера, ни на стороне Pyrus.
